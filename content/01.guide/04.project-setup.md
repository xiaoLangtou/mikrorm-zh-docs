## Fastify

让我们在 `src` 目录中创建新文件 `app.ts`，并从中导出一个 `bootstrap` 函数，在其中创建 fastify app 实例。还记得我们如何通过 fork [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 来绕过全局上下文验证吗？对于 Web 服务器，我们可以利用中间件，或者在 fastify 中使用 hook，来自动实现唯一的请求上下文。MikroORM 提供了一个名为 `RequestContext` 的便捷 helper，可用于为每个请求创建 fork。[`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 知道这个类，并尝试自动从中获取正确的上下文。

_Let's create new file `app.ts` inside `src` directory, and export a `bootstrap` function from it, where we create the fastify app instance. Remember how we were forking the [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) to get around the global context validation? For web servers, we can leverage middlewares, or in fastify hooks, to achieve unique request contexts automatically. MikroORM provides a handy helper called `RequestContext` which can be used to create the fork for each request. The [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) is aware of this class and tries to get the right context from it automatically._

:::caution 警告 / Caution：`RequestContext` helper 如何工作？ / How does `RequestContext` helper work?

在内部，所有使用 Identity Map 的 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 方法（例如 [`em.find()`](#find) 或 [`em.getReference()`](#getReference)）首先调用 `em.getContext()` 来访问上下文 fork。此方法将首先检查我们是否在 `RequestContext` 处理程序内运行，并优先使用来自它的 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) fork。

```ts
// 我们在全局 EM 实例上调用 em.find()（we call em.find() on the global EM instance）
const res = await orm.em.find(Book, {});

// 但在底层这解析为（but under the hood this resolves to）
const res = await orm.em.getContext().find(Book, {});

// 然后解析为（which then resolves to）
const res = await RequestContext.getEntityManager().find(Book, {});
```text

然后 `RequestContext.getEntityManager()` 方法检查我们在 `RequestContext.create()` 方法中用于创建新 EM fork 的 `AsyncLocalStorage` 静态实例。

_The `RequestContext.getEntityManager()` method then checks `AsyncLocalStorage` static instance we use for creating new EM forks in the `RequestContext.create()` method._

Node.js 核心的 [`AsyncLocalStorage`](https://nodejs.org/api/async_context.html#class-asynclocalstorage) 类是这里的魔术师。它允许我们在整个异步调用过程中跟踪上下文。它允许我们将 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) fork 的创建（通常在中间件中，如上一节所示）与通过全局 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 实例使用它解耦。

_The [`AsyncLocalStorage`](https://nodejs.org/api/async_context.html#class-asynclocalstorage) class from Node.js core is the magician here. It allows us to track the context throughout the async calls. It allows us to decouple the [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) fork creation (usually in a middleware as shown in the previous section) from its usage through the global [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) instance._

:::

  // ...

}

_Let's add our first endpoint - `GET /article` which lists all existing articles. It is a public endpoint that can take `limit` and `offset` query parameters and return requested items together with the total count of all available articles._

我们可以使用 `em.count()` 来获取 Entity 的数量，但由于我们想要在分页的 Entity 列表旁边返回计数，我们有一个更好的方法——`em.findAndCount()`。此方法恰好服务于此目的，返回分页列表和项的总计数。

_We could use `em.count()` to get the number of entities, but since we want to return the count next to the paginated list of entities, we have a better way - `em.findAndCount()`. This method serves exactly this purpose, retuning the paginated list with the total count of items._

```ts title='app.ts'
app.get('/article', async request => {
  const { limit, offset } = request.query as { limit?: number; offset?: number };

## 基本的依赖注入容器

在我们测试第一个端点之前，让我们进行一些重构，使设置更具前瞻性。添加一个新的 `src/db.ts` 文件，它将作为一个简单的依赖注入（DI）容器。它将导出 `initORM()` 函数，该函数将首先初始化 ORM 并将其缓存到内存中，因此后续调用将返回相同的实例。得益于顶层 await，我们可以直接初始化 ORM 并导出它，但很快我们将希望在此之前修改一些选项，以用于测试目的，拥有这样的函数将有助于实现这一目标。
 
_Before we get to testing the first endpoint, let's refactor a bit to make the setup more future-proof. Add a new `src/db.ts` file, which will serve as a simple Dependency Injection (DI) container. It will export `initORM()` function that will first initialize the ORM and cache it into memory, so the following calls will return the same instance. Thanks to top-level await, we could just initialize the ORM and export it right ahead, but soon we will want to alter some options before we do so, for testing purposes, and having a function like this will help in achieving that._

> 请注意，我们从 `@mikro-orm/sqlite` 包导入所有的 `EntityManager`、`EntityRepository`、`MikroORM`、`Options`——这些导出都是针对 `SqliteDriver` 类型化的。
>
> Note that we are importing all of `EntityManager`, `EntityRepository`, `MikroORM`, `Options` from the `@mikro-orm/sqlite` package - those exports are typed to the `SqliteDriver`.

```ts title='db.ts'
import { EntityManager, EntityRepository, MikroORM, Options } from '@mikro-orm/sqlite';

export interface Services {
  orm: MikroORM;
  em: EntityManager;
  article: EntityRepository<Article>;
  user: EntityRepository<User>;
  tag: EntityRepository<Tag>;
}

let cache: Services;

export async function initORM(options?: Options): Promise<Services> {
  if (cache) {
    return cache;
  }

  const orm = await MikroORM.init(options);

  // save to cache before returning
  return cache = {
    orm,
    em: orm.em,
    article: orm.em.getRepository(Article),
    user: orm.em.getRepository(User),
    tag: orm.em.getRepository(Tag),
  };
}
```

并在 `app.ts` 文件中使用它，而不是直接初始化 ORM：

_And use it in the `app.ts` file instead of initializing the ORM directly:_

```ts title='app.ts'
import { RequestContext } from '@mikro-orm/core';
import { fastify } from 'fastify';
import { initORM } from './db.js';

export async function bootstrap(port = 3001) {
  const db = await initORM();
  const app = fastify();

  // register request context hook
  app.addHook('onRequest', (request, reply, done) => {
    RequestContext.create(db.em, done);
  });

  // shut down the connection when closing the app
  app.addHook('onClose', async () => {
    await db.orm.close();
  });

  // register routes here
  app.get('/article', async request => {
    const { limit, offset } = request.query as { limit?: number; offset?: number };
    const [items, total] = await db.article.findAndCount({}, {
      limit, offset,
    });

    return { items, total };
  });

  const url = await app.listen({ port });

  return { app, url };
}
```

:::caution 警告 / Caution：从 driver 包导入 `EntityManager` 和 `EntityRepository` / Importing `EntityManager` and `EntityRepository` from a driver package

虽然 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 和 [`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) 类由 `@mikro-orm/core` 包提供，但那些只是基础——driver 无关的——实现。这意味着什么的一个例子是 `QueryBuilder`——作为 SQL 概念，它在 `@mikro-orm/core` 包中没有位置，相反，[`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 的扩展称为 `SqlEntityManager` 由 SQL driver 包提供（它在 `@mikro-orm/knex` 包中定义，并在依赖于它的每个 SQL driver 包中重新导出）。这个 `SqlEntityManager` 类提供了额外的 SQL 相关方法，例如 `em.createQueryBuilder()`。

_While [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) and [`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) classes are provided by the `@mikro-orm/core` package, those are only the base - driver agnostic - implementations. One example of what that means is the `QueryBuilder` - as an SQL concept, it has no place in the `@mikro-orm/core` package, instead, an extension of the [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) called `SqlEntityManager` is provided by the SQL driver packages (it is defined in `@mikro-orm/knex` package and reexported in every SQL driver packages that depend on it). This `SqlEntityManager` class provides the additional SQL related methods, like `em.createQueryBuilder()`._

_For convenience, the `SqlEntityManager` class is also reexported under [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) alias. This means we can do `import { EntityManager } from '@mikro-orm/sqlite'` to access it._

_Under the hood, MikroORM will always use this driver-specific [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) implementation (you can verify that by `console.log(orm.em)`, it will be an instance of `SqlEntityManager`), but for TypeScript to understand it, you will need to use the driver package to import it. The same applies to the [`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) and `SqlEntityRepository` classes._

```ts
import { EntityManager, EntityRepository } from '@mikro-orm/sqlite'; // or any other driver package
```

你也可以使用从 driver 包导出的 `MikroORM`、`defineConfig` 和 `Options`，它们的工作原理类似，提供 driver 类型而无需使用泛型。

_You can also use `MikroORM`, `defineConfig` and `Options` exported from the driver package, it works similarly, providing the driver type without the need to use generics._

:::

### 什么是 `EntityRepository`

Entity repository 是 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 之上的薄层。它们作为扩展点，因此你可以添加自定义方法，甚至更改现有方法。默认的 [`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) 实现只是将调用转发给底层的 [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) 实例。

Entity repositories are thin layers on top of [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager). They act as an extension point, so you can add custom methods, or even alter the existing ones. The default [`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) implementation just forwards the calls to the underlying [`EntityManager`](https://mikro-orm.io/api/core/class/EntityManager) instance.

[`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) 类携带 Entity 类型，所以我们不必在每次 `find` 或 `findOne` 调用中传递它。

[`EntityRepository`](https://mikro-orm.io/api/next/core/class/EntityRepository) class carries the entity type, so we do not have to pass it to every `find` or `findOne` calls.

请注意，没有“刷新 repository”这种事情——它只是 [`em.flush()`](#flush) 的快捷方式。换句话说，我们总是刷新整个 Unit of Work，而不仅仅是这个 repository 表示的单个 Entity。

Note that there is no such thing as "flushing a repository" - it is just a shortcut to [`em.flush()`](#flush). In other words, we always flush the whole Unit of Work, not just a single entity that this repository represents.

### 关于单元测试的说明

跳过一些不需要数据库连接的单元测试中的 `MikroORM.init()` 阶段可能很诱人，但 `init` 方法**做的不仅仅是**建立连接。该方法最重要的部分是 metadata 发现，其中 ORM 检查所有 Entity 定义并为各种 metadata 选项（主要是命名策略和双向关系）设置默认值。

It  might be tempting to skip the `MikroORM.init()` phase in some of your unit tests that do not require database connection, but the `init` method is **doing more** than just establishing that. The most important part of that method is metadata discovery, where the ORM checks all the entity definitions and sets up the default values for various metadata options (mainly for naming strategy and bidirectional relations).

发现阶段对于[propagation](../propagation.md)的工作是**必需的**。但不用担心，你可以在不连接到数据库的情况下初始化 ORM，只需在 ORM 配置中提供 `connect: false`：

The discovery phase is **required for [propagation](../propagation.md) to work**. But worry not, you can initialize the ORM without connecting to the database, just provide `connect: false` to the ORM config:

```ts
const orm = await MikroORM.init({
  // ...
  connect: false,
});
```

从 v6 开始，你还可以使用新的 `initSync()` 方法来同步实例化 ORM。这将仅运行发现，并跳过数据库连接。当你首次尝试查询数据库（或以任何需要连接的方式使用它）时，ORM 将懒惰地连接到它。

Since v6, you can also use the new `initSync()` method to instantiate the ORM synchronously. This will run the discovery only, and skip the database connection. When you first try to query the database (or work with it in any way that requires the connection), the ORM will connect to it lazily.

> 同步方法永远不会连接到数据库，所以 `connect: false` 是隐式的。
>
> The sync method never connects to the database, so `connect: false` is implicit.

```ts
const orm = MikroORM.initSync({
  // ...
});
```

## SchemaGenerator

在指南的早些时候，当我们需要创建测试数据库时，我们使用 `SchemaGenerator` 重新创建数据库。让我们更多地讨论一下这个类。

Earlier in the guide, when we needed to create the database for testing, we used the `SchemaGenerator` to recreate our database. Let's talk a bit more about this class.

[`SchemaGenerator`](../schema-generator) 负责基于你的 Entity metadata 生成 SQL 查询。换句话说，它将 Entity 定义转换为数据定义语言（DDL）。此外，它还可以理解你当前的数据库 schema 并将其与 metadata 进行比较，生成使你的 schema 保持同步所需的查询。

[`SchemaGenerator`](../schema-generator) is responsible for generating the SQL queries based on your entity metadata. In other words, it translates the entity definition into the Data Definition Language (DDL). Moreover, it can also understand your current database schema and compare it with the metadata, resulting in queries needed to put your schema in sync.

它可以以编程方式使用：

It can be used programmatically:

```ts
// 获取查询
// to get the queries
const diff = await orm.schema.getUpdateSchemaSQL();
console.log(diff);

// 或运行查询
// or to run the queries
await orm.schema.updateSchema();
```

> 使用 `orm.schema.updateSchema()` 你可以轻松设置与 TypeORM 通过 `synchronize: true` 相同的行为，只需在 ORM 初始化后（或在某些应用程序引导代码中）将其放入你的应用程序中。请记住，这种方法可能具有破坏性且不被鼓励——你应该始终验证 `SchemaGenerator` 在运行之前生成的查询！
>
> With the `orm.schema.updateSchema()` you could easily set up the same behavior as TypeORM has via `synchronize: true`, just put that into your app right after the ORM gets initialized (or into some app bootstrap code). Keep in mind this approach can be destructive and is discouraged - you should always verify what queries the `SchemaGenerator` produced before you run them!

或通过 CLI：

Or via CLI:

> 要运行查询，请将 `--dump` 替换为 `--run`。
>
> To run the queries, replace `--dump` with `--run`.

```bash

> If this command does not work and produces some invalid queries, you can always recreate the schema from scratch, by first calling `schema:drop --run`.

使用 `SchemaGenerator` 在原型设计初始应用程序时可能很方便，或者特别是在测试时，你可能希望拥有许多具有最新 schema 的数据库，而不管你的生产 schema 看起来如何。但要注意，当在真正的生产数据库上使用时，它可能非常危险。幸运的是，我们有一个解决方案——migration。

Working with `SchemaGenerator` can be handy when prototyping the initial app, or especially when testing, where you might want to have many databases with the latest schema, regardless of how your production schema looks like. But beware, it can be very dangerous when used on a real production database. Luckily, we have a solution for that - the migrations.

## Migrations

> 要使用 migration，你首先需要为 SQL driver 安装 `@mikro-orm/migrations` 包（或为 MongoDB 安装 `@mikro-orm/migrations-mongodb`），并在你的 ORM 配置中注册 `Migrator` 扩展。
>
> To use migrations you first need to install `@mikro-orm/migrations` package for SQL drivers (or `@mikro-orm/migrations-mongodb` for MongoDB), and register the `Migrator` extension in your ORM config.

MikroORM 对通过 [umzug](https://github.com/sequelize/umzug) 的 migration 提供集成支持。它允许你使用当前 schema 差异生成 migration，以及管理它们的执行。默认情况下，每个 migration 都将在一个事务内执行，并且所有它们都将被包装在一个主事务中，所以如果其中一个失败，一切都将被回滚。

MikroORM has integrated support for migrations via [umzug](https://github.com/sequelize/umzug). It allows you to generate migrations with current schema differences, as well as manage their execution. By default, each migration will be executed inside a transaction, and all of them will be wrapped in one master transaction, so if one of them fails, everything will be rolled back.

### 初始 migration

如果你想开始使用 migration，而你已经生成了 schema，`--initial` 标志将帮助保持现有 schema，同时仅基于 Entity metadata 生成第一个 migration。它只能在 schema 为空或完全最新时使用。如果你的 schema 已经存在，生成的 migration 将自动标记为已执行——如果没有，你将需要像任何其他 migration 一样手动执行它，通过 `npx mikro-orm-esm migration:up`。

If you want to start using migrations, and you already have the schema generated, the `--initial` flag will help with keeping the existing schema, while generating the first migration based only on the entity metadata. It can be used only if the schema is empty or fully up-to-date. The generated migration will be automatically marked as executed if your schema already exists - if not, you will need to execute it manually as any other migration, via `npx mikro-orm-esm migration:up`.

> 只有在之前没有生成或执行过 migration 的情况下才能创建初始 migration。如果你是从头开始的，而且还没有 schema，你不需要使用 `--inital` 标志，常规 migration 也能完成这项工作。
>
> Initial migration can be created only if there are no migrations previously generated or executed. If you are starting fresh, and you have no schema yet, you don't need to use the `--inital` flag, a regular migration will do the job too.

```sh
npx mikro-orm-esm migration:create --initial
```

这将在 `src/migrations` 目录中创建初始 migration，包含来自 `schema:create` 命令的查询。因为我们的 schema 已经同步，该 migration 将自动被标记为已执行。

This will create the initial migration in the `src/migrations` directory, containing queries from `schema:create` command. The migration will be automatically marked as executed because our schema was already in sync.

### Migration 类

让我们看一下生成的 migration。你可以看到有一个类扩展了来自 `@mikro-orm/migrations` 包的 `Migration` 抽象类：

```ts title='Migration20220913202829.ts'

export class Migration20220913202829 extends Migration {

  async up(): Promise<void> {
    this.addSql('create table `tag` (`id` integer not null primary key autoincrement, `created_at` datetime not null, `updated_at` datetime not null, `name` text not null);');
    // ...
  }

}
```

为了支持撤消这些更改，你可以实现 `down` 方法，该方法默认情况下会抛出错误。

To support undoing those changed, you can implement the `down` method, which throws an error by default.

:::caution 警告 / Caution：Down migration 和 SQLite / Down migrations and SQLite

MikroORM 将自动生成 down migration（尽管出于安全考虑不会为初始 migration 生成），有一个例外——SQLite driver，由于其功能有限。如果你使用任何其他 driver，将生成 down migration（除非它是初始 migration）。

MikroORM will automatically generate down migrations (except for initial migrations, for safety reasons), with one exception - the SQLite driver due to its limited feature set. If you use any other driver, down migrations will be generated (unless it's an initial migration).

:::

> 你还可以通过 `this.execute('...')` 在 `up()`/`down()` 方法内执行查询，这将在与 migration 的其余部分相同的事务中运行查询。`this.addSql('...)`方法也接受 knex 的实例。可以通过 `this.getKnex()` 访问 Knex 实例。
>
> You can also execute queries inside the `up()`/`down()` method via `this.execute('...')`, which will run queries in the same transaction as the rest of the migration. The `this.addSql('...)` method also accepts instances of knex. Knex instance can be accessed via `this.getKnex()`;

### 自动运行 migration

在我们收工之前，让我们自动运行 migration——我们可以以编程方式使用 `Migrator`，与 `SchemaGenerator` 类似。我们希望在应用程序引导周期期间运行它们，在它开始接受连接之前，所以一个好的地方是我们的 `bootstrap` 函数，就在我们初始化 ORM 之后。

Before we call it a day, let's automate running the migrations a bit - we can use the `Migrator` programmatically, in a similar way like the `SchemaGenerator`. We want to run them during our app bootstrap cycle, before it starts to accept connections, so a good place for that is our `bootstrap` function, right after we initialize the ORM.

```ts title='app.ts'
export async function bootstrap(port = 3001, migrate = true) {
  const db = await initORM();

  if (migrate) {
    // 同步 schema
    // sync the schema
    await db.orm.migrator.up();
  }

  // ...
}
```

我们需要有条件地执行此操作，因为我们只想为生产数据库运行 migration，而不是我们的测试数据库（因为它们直接使用 `SchemaGenerator`，与 `Seeder` 一起）。不要忘记在从测试用例调用 `bootstrap()` 函数时传递 `false`：

We need to do this conditionally, as we want to run the migrations only for the production database, not for our testing ones (as they use the `SchemaGenerator` directly, together with the `Seeder`). Don't forget to pass `false` when calling the `bootstrap()` function from our test case:

```ts title='utils.ts'
export async function initTestApp(port: number) {
  const { orm } = await initORM({ ... });

  await orm.schema.createSchema();
  await orm.seeder.seed(TestSeeder);

  const { app } = await bootstrap(port, false); // <-- 这里
  // const { app } = await bootstrap(port, false); // <-- here

  return app;
}
```
